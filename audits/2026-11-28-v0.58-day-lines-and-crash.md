## The crash (issue #88)
- **What the report had:** only the bottom 38 lines of a 300-line stack trace, in R8's short names. The error itself was cut off (R1).
- **Reading it:**
  - a CI runner rebuilt v0.57.0's R8 map: `pg_map_id` e2c4678e623d…, the same as the crash's;
  - the map names the frames: the chat's list measuring its rows (`LazyListState` → `MeasurePassDelegate` → `FillNode`, `PaddingNode`, `graphicsLayer`), started by the chat's keep-at-the-end scroll (`Conversation$8$1$4`).
- **The cause:**
  - two rows in a chat took their height from the media's own shape, with no limit: a GIF playing in its bubble (`aspectRatio` from the video's size) and a GIF's first frame (`ContentScale.FillWidth`);
  - in a list a row has no height limit, so a GIF or video with an absurd or broken size (1 by 2000) asks for a height Compose can't hold;
  - a scratch test of the old still-frame code in a list failed with `IllegalArgumentException: Can't represent a width of 600 and height of 1200000 in Constraints`, the same kind of crash inside the list's measure;
  - every other media row has a fixed size.
- **Fix:**
  - `Moving.bubbleRatio` keeps a video's or GIF's shape between 9:16 and 21:9; an unknown size gets 16:9 (tested);
  - `VideoSurface` uses it, and logs an odd size to the problem report;
  - `GifStill` crops the first frame to it. `GifStillTest` puts a 4×8000 frame in a list and checks the height stays at 16:9 of the width at most.
- **Not certain:** the top of the crash was cut, so this is the cause the frames and the test point to, not one read from the error line. The tablet's own report still has the error line. If Oiê closes again in that group, v0.58's report keeps the error and its causes, and the release keeps its map (R1, R2), so the next report can be read straight away.

| ID | Severity | Finding | Fix | Status |
|---|---|---|---|---|
| C1 | P0 | Opening a group chat with a GIF or video of an odd size closed Oiê. | Media shape kept between 9:16 and 21:9 in bubbles. | Fixed, tested |


## Update, v0.59.0 (same day): the real cause
v0.58's report kept the error, and issue #90 showed it at once: `IllegalArgumentException: Key "AC8B09F2…" was already used`. The same WhatsApp message (a 32-character id) was stored twice in the group, and the chat's list can't hold one key twice.
- **Root cause:** `AppState.receive` added every message the link delivered. WhatsApp delivers a message again after a reconnect, so a busy group got one in twice. The copy was saved, so the chat crashed every time it opened. Issue #88's frames, the chat's list measuring, fit this too. The GIF shape (C1) was a real gap in the same place, but not this crash: its finding stands as a hardening, and the claim that it fixed #88 is withdrawn.
- **Fix, in three places:**
  - `receive` drops a message whose id is already in the chat, so it isn't notified, downloaded or marked read again;
  - `Codec.decode` keeps the first copy of each (chat, id) already saved;
  - `visible()` lists each id once, a guard for the chat's list and the Fotos grid, the only two lists keyed on message ids.
- **Tests:**
  - `DuplicateChatTest` opens the real chat with a message saved twice. It failed with the tablet's exact error before the fix and passes after.
  - `DuplicateMessageTest` (4) covers arriving twice, cleaning on load, the same id in two chats (kept), and the visible list.
- **Flows and copy:** no screen or copy changes; the flow doc gains the rule. The ux-user-flows, graphic-design and less-is-more checks are unaffected (nothing shown changes).

| ID | Severity | Finding | Fix | Status |
|---|---|---|---|---|
| C2 | P0 | A message delivered twice was stored twice, and its chat closed Oiê on every opening (issues #88, #90). | Dropped on arrival, cleaned on load, listed once. | Fixed, tested (fails before, passes after) |
| C1 | P2 (was P0) | GIF and video shapes could ask a chat for an unmeasurable height. | v0.58's clamp. | Fixed; not the cause of #88 |
